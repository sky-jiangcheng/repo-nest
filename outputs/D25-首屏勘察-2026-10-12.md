# D25 首屏勘察报告（只读，2026-10-12）

勘察范围：`/Users/jiangcheng/Workspace/Script/repotory`。目标：为「D25 首屏界面对齐」提供可实现的事实底座。目标形态已由 ADR-0017 定死，本报告只记录现状与缺口，不做设计。

## 0. 结论摘要（高置信）

1. 首屏（路由 `/`）当前是 **Knowledge（知识库）页**，不是 Dashboard；`/dashboard` 是独立路由。ADR-0017 要求路由默认页改为「记忆环 + 项目状态」并排首屏。
2. 记忆环两个数据源：**全局检索已有完整链路**（`SearchAll`：笔记+todo，前端 `searchAll` 已被 CommandPalette 与知识库页使用）；**「最近 handoff」只有单条方法 `LatestHandoff`**（后端绑定已在、前端未封装），**「列最近 N 条 handoff」的方法不存在**，且现有 `ListNotes`/`ListAllNotes` 均不支持按 tags 过滤——这是唯一确定的后端缺口。
3. handoff 笔记识别方式：tags 含保留标签 `handoff`（自动捕捉的另有 `auto-captured`），kind 固定为 `knowledge`，与普通知识笔记同 kind，**不能靠 kind 区分**。
4. i18n：单命名空间 `common`，中英两份 JSON；CSS：全局 API 类在 `shared.css`，组件级一律 CSS Modules，跨层引用用 `:global()`。
5. 实现风险 top3：① Dashboard 无专属组件测试（仅 App.smoke），ADR 晋升条件要求「记忆环与仪表盘两处功能测试全绿」；② `ListAllNotes` 无界（全量加载），首屏若靠它过滤 handoff 需评估数据量；③ service `SearchNotes` 注释声称搜 tags，但 FTS/LIKE 实际只索引 title+content，注释与代码冲突（见 §6.3）。

## 5. 「最近 handoff」的数据形态

### 5.1 handoff 笔记怎么识别

- **保留标签 `handoff`**：`internal/service/handoff.go:15` `const handoffTag = "handoff"`；写入时 tags 固定以它开头，可附加用户标签（:63-65 `tags := handoffTag; if extra != "" { tags = tags + ", " + extra }`）。
- **kind 固定 `"knowledge"`，source 固定 `"mcp"`**：`handoff.go:68` `s.CreateNoteWithMeta(in.ProjectID, title, renderHandoffMarkdown(...), tags, "knowledge", "mcp")` —— 无论来源是 MCP 的 `repotory_handoff` 还是 Claude 捕捉，都走同一路径。**不能靠 kind 区分 handoff 与普通知识笔记。**
- **自动捕捉的附加标签 `auto-captured`**：`internal/service/handoff_capture.go:105` `Tags: "auto-captured"`（与 handoffTag 合并为 `handoff, auto-captured`），Agent 名 `"claude-code"`（:118 一带）。
- **config 键 `claude_session_capture`**：`handoff_capture.go:15` `const claudeCaptureConfigKey = "claude_session_capture"`，值必须恰为 `"1"` 才开启（:16-19，默认关，ADR-0010 的 C 端 opt-in）。
- 标题格式：`Session Handoff 2006-01-02 15:04`（`handoff.go:78`）；正文为固定 Markdown 模板（`# Session Handoff` + Summary/Changes/Decisions/Gotchas/Next Steps 节，`handoff.go:138-176` 一带 `renderHandoffMarkdown`）。
- DB 层识别 SQL：`internal/db/notes.go:146-147` `WHERE ',' || REPLACE(LOWER(tags), ' ', '') || ',' LIKE '%,handoff,%'` —— 逗号分隔标签的精确匹配，排序 `ORDER BY updated_at DESC, id DESC LIMIT 1`（:152）。

### 5.2 「列最近 N 条 handoff」存在吗

**不存在。** 全库 grep `ListHandoffs|RecentHandoffs|handoffs` 只命中 context 组装里的 `splitHandoffNotes`（`internal/service/context.go:281-284`，那是把一个项目现有笔记拆成 handoff/普通两组的内存操作，不是列表查询）。现有能力边界：

- `LatestHandoff`（service/绑定都有）→ 只给**全局或单项目 1 条**状态（无正文）。
- `ListNotes(projectID)`（`internal/db/notes.go:121-140`）→ 只按 projectID，排序 `pinned DESC, sort_order ASC, created_at ASC, id ASC`（:124），**无 kind/tags 过滤、无 limit、无全局模式**。不能支撑「最近 N 条 handoff」。
- `ListAllNotes(limit, kind)`（`internal/db/notes.go:308`）→ 有 limit 与 kind 过滤，但 handoff 的 kind 是 `knowledge`，**按 kind 过滤会混入全部知识笔记；不支持 tags 过滤**。

**可行的支撑路径**（供设计阶段选择，按改动面从小到大）：

1. **纯前端**：`listAllNotes()` 全量拉取后客户端过滤 `tags` 含 `handoff` 再按 `updated_at` 排序取前 N。先例：`useKnowledgePage.ts:126-131` 的 `recentNotes`（全量排序取 5）。缺点：无界加载，知识库大了浪费。
2. **新绑定（推荐档）**：仿 `LatestHandoffNote`（`internal/db/notes.go:142`）写 `ListRecentHandoffNotes(db, limit, projectID)`（同一 tags LIKE 条件 + `ORDER BY updated_at DESC, id DESC LIMIT ?`），service 包一层 `ListRecentHandoffs(limit) ([]domain.NoteWithProject, error)`，绑定 `ListRecentHandoffs(limit int) []service.HandoffStatus 或 []domain.NoteWithProject`，并**在 P32 审计块登记**（建议归入 :57 IDE chrome 旁或新起 Memory 组，理由：首屏记忆环人侧展示）。
3. 复用 `LatestHandoff(0)` 只展示 1 条 + `searchNotes` 兜底，功能上不满足「环」的多条诉求。

## 6. 全局检索现状

### 6.1 service 签名与范围

- `service.SearchNotes(query string) []domain.SearchHit`（`internal/service/search.go:14`）→ `db.SearchNotes`（`internal/db/search.go:21`）：**只搜笔记**。FTS5 trigram 索引（`internal/db/migrate.go:28`：`fts5(title, content, content='project_notes', …, tokenize='trigram')`），查询词全部 ≥3 字符走 FTS（bm25 排序，:53-82），否则/失败回退 LIKE（:84-114，合成权重：标题命中 > 正文，pinned 加权，新近加分）。结果上限 `searchResultLimit = 20`（:12），snippet 窗口 100 字符（:13），带 `<mark>` 高亮（`makeSnippet`/`highlightQuery`，:220-247）。M3-C 松弛：严格 AND 空结果时去停用词转 OR（:30-36, `escapeFTSOR` :185-200）。
- `service.SearchAll(query string) []domain.SearchHit`（`search.go:31`）→ `db.SearchAll`（`db/search.go:119-134`）：**笔记 + todo**（todo 走 `project_todos_fts`/LIKE，:136-190）。**不包含 wiki 页。**
- **wiki 页搜索未对 UI 暴露**：`db.SearchWikiPages`（`internal/db/wiki_fts.go:91`，只搜 `status='approved'` 页）仅被 W2 证据检索内部使用（`internal/service/wiki_evidence.go:167`）与测试引用，无 service 方法、无绑定。若 D25 的「全局检索」要含 wiki 页，这是一处需要新增的缺口（否则现状即「笔记+todo」口径）。

### 6.2 前端调用方

- `searchAll`：CommandPalette（`web/src/components/CommandPalette.tsx:3,60`——⌘K 全局搜索，**新首屏的全局检索可参考/复用此交互**）；知识库页（`web/src/hooks/useKnowledgePage.ts:60`）。
- `searchNotes`：endpoints 有封装（`web/src/api/endpoints.ts:196-202`，`/notes/search?q=`）但当前**无页面使用**（grep 仅测试引用）。
- 端点声明：`web/src/api/endpoints.ts:190-203`——`searchNotes(query)` method `'SearchNotes'` path `/notes/search?q=`；`searchAll(query)` method `'SearchAll'` path `/search?q=`。

### 6.3 注释与代码的冲突（如实记录）

`internal/service/search.go:13` 注释称「SearchNotes searches note **content/title/tags**」，但 FTS 表只建了 `title, content` 两列（`internal/db/migrate.go:28`），LIKE 回退也只匹配 `title LIKE … OR content LIKE …`（`db/search.go:125-126`）。**实际搜索范围 = title + content，不含 tags**（按证据分级：一手代码 > 注释）。设计检索入口文案时勿按注释承诺 tags 命中。

## 7. endpoints 声明模式与 i18n

### 7.1 endpoints.ts 模式（`web/src/api/endpoints.ts`）

- 每个后端调用一个具名函数，统一走 `call<T>({method, args, path, init})`（transport 双模式：Wails 下直接 `window.go.app.App[method](...args)`（`web/src/api/transport.ts:22-34`）；浏览器下 POST `/api/rpc` `{method, args}` JSON-RPC（:37-51, :64-79）。**path/init 在 RPC 模式不参与派发，仅为兼容保留**——新增绑定只需 method+args，无需新增 REST 路由；`/api/rpc` 用反射枚举 App 全部导出方法（`internal/httpapi/server.go:29,40-45,52`）。
- 列表型返回一律 `.then(d => d ?? [])` 兜底（如 `searchNotes` :202、`listNotes` :361）；可选对象型内联空对象兜底（如 `getSummary` :154-159）。
- barrel 导出：`web/src/api/client.ts` 转 types/transport/endpoints；页面只 import from `../api/client`。
- POST/PUT 动作：`init: { method: 'POST' }` 或 `jsonInit('POST', body)`（:18-21）。

### 7.2 i18n

- 入口：`web/src/i18n/index.ts`——单命名空间 `common`，语言检测 `navigator.language` + localStorage `repotory-language`，fallback `en`。
- **中英两份**：`web/src/locales/zh-CN/common.json`（696 行）、`web/src/locales/en/common.json`（697 行）。key 按区块嵌套（`nav` :2-10、`dashboard` :12-63、`knowledge` :64 起、`settings` :101 起）。**添加 key 的方式：两份 JSON 的对应区块各加一条**，代码里用 `t('dashboard.xxx', { defaultValue: '…' })`（现有惯例：组件内 defaultValue 全部内联，见 Dashboard.tsx 各处）。
- App.smoke 测试会抓「key 渲染成原文」这类失败（`web/src/App.smoke.test.tsx:1-9`），漏加 key 有回归网。

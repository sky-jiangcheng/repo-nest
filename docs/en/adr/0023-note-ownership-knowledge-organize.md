# ADR-0023: Note ownership and knowledge-base organize — imports stop silently dropping knowledge, floating knowledge gets a landing spot and a way home

## Background

The user's original complaint was that "notes and projects aren't directly associated." Decomposed onto the code, that one sentence exposes four independent problems:

1. **When an import matches no project, the knowledge is silently dropped — it does not become a "headless note."** `project_notes.project_id` is `INTEGER NOT NULL` with a foreign key (`internal/db/db.go:193-205`); there is no "note without an owner" state at all. An importer that matches nothing returns `ProjectID: 0` (`internal/importers/memsrc/memsrc.go:25`), and the runtime drops it at `internal/core/plugin/runtime/runtime.go:227-229`: `if d.ProjectID <= 0 { run.Skipped++ }`. The supposed "headless notes" never existed in the database — the 41 notes AI1 lost in the 2026-10-14 incident were partly this same class of dropped knowledge.
2. **Clicking a note in the knowledge base jumps only to its project, not to the note itself** (`web/src/pages/knowledge/KnowledgeCard.tsx:48` carries only `project_id`).
3. **A project cannot express "which repo I came from / whether I'm an import placeholder"**: the `projects` table has no kind column and no repo-binding field (`internal/domain/types.go:9-19`; the hard-coded column list `projectColumns` lives at `projects.go:13`); "All projects" is a front-end filter sentinel `value=0` (`web/src/pages/Review.tsx:227`), not a real row; and there is **no "default project" row** either — `insertDefaults` (`internal/db/migrate.go:544`) seeds only `app_config`, never a project.
4. **The cleanup logic fails on both ends**: `CleanupStaleDataTx` (`internal/db/cleanup.go:50-54`) deletes only projects with no repos **and** no notes **and** no todos — so a placeholder whose repo has vanished from scanning but that still holds notes **lingers forever**; conversely a not-yet-used **empty "default project" gets deleted by that same clause**.

"If an import finds no project it should still land somewhere; clicking a note should reach the note; floating knowledge should be assignable" is a coupled set of needs sharing one data-model gap: projects lack an expression of "origin and role." This ADR fixes the shape of that gap and the landing strategy; it lands no code.

## Prior art (copy the mechanism, not the stack)

- **Our own `wiki_pages` global tier**: the page layer already has a nullable `project_id` + `COALESCE(project_id,0)` "GLOBAL tier" (`internal/db/wiki.go:46,241`), and `internal/app/bindings.go:528` notes that "projectID 0 is GLOBAL tier, not every project" — that is the reference for a nullable/sentinel route at the note layer. This ADR deliberately does **not** take that route; see the options matrix.
- **Our own `SplitProjectDown`**: the precedent of building a project from the repo base name with the repo path as `root_path`; placeholders reuse it directly.
- **Our own `note_versions` human gate / ADR-0019 merge**: destructive consolidation (merging, deleting notes) is always human-triggered, never automatic.

## Decision

**1. Add a `project_kind` column to `projects`, valued `scanned` / `import_placeholder` / `default`.** The migration uses `ALTER TABLE projects ADD COLUMN project_kind TEXT NOT NULL DEFAULT 'scanned'` (a constant default satisfies SQLite's rule that a NOT NULL added column must have a non-NULL default). **The value set is validated in Go; the migration deliberately adds no inline CHECK / table-level constraint** — adding or changing a CHECK on an existing table forces a full table rebuild (an established lesson in this repo, see MEMORY / ADR-0021 implementation corrections), and Go validation suffices for a pure classification column. The **hard failure points** when adding the column (missing any one breaks the build or runtime): the `projectColumns` constant (`projects.go:13`, shared by the Scan sites in `GetAllProjects` / `GetStarredProjects` / `GetProjectByID` / `SearchProjects`) and the `domain.Project` struct (`types.go:9-19`) must both be extended, and `ExpectedSchemaVersion` in `internal/integrity/checks.go:49` advances from 23 to 24 with a reversible-migration test, or the full `go test -race` suite goes red.

**2. Idempotently seed one `kind='default'` "Uncategorized" project in the migration** as the fallback landing spot and organize target. Its `root_path` is a synthetic sentinel no real filesystem path can produce (recommended: `repotory://memory/default`), satisfying `root_path NOT NULL UNIQUE` while never colliding with a scanned repo. The display name "Uncategorized" is localized by the front-end based on `kind='default'`; **no locale key is stored in a data column** (the data layer keeps one fixed internal name; bilingualism happens only at the UI). The seed uses `INSERT ... WHERE NOT EXISTS (SELECT 1 FROM projects WHERE project_kind='default')` for idempotency.

**3. Change the import landing to a "mixed" model, eliminating silent drops.** Add `RepoPath` / `RepoName` fields to `plugin.ImportDoc` (`internal/core/plugin/plugin.go:45`) — each source derives them from `cwd` / `folder` / mangled directory name (the `LastPathSegment` helper already exists in `memsrc`). Rewrite the `ProjectID<=0 → skip` branch at `runtime.go:227` into a landing decision — the decision lives in the runtime because that is where `r.db` is held, whereas `memsrc.MatchProject` only takes slices and has no `*sql.DB`:
- sources **with a repo path** (codex / cursor / claude / opencode / codebuddy) → call a new db helper `EnsureImportPlaceholderTx`, which upserts a `kind='import_placeholder'` project by `root_path` and back-fills `doc.ProjectID`;
- global-memory sources with **no repo path** (openclaw / hermes / codebuddy-memory, which only ever have a configurable target project and no per-project path) → back-fill the default project id. **codebuddy-memory is thereby folded into the unified landing**: it previously did an intentional early `return docs, nil` when no target was configured (its importer's comment + the "unconfigured→0→skip" semantics of `memsrc.TargetProject`); it now lands on "Uncategorized" — that guard's intent was to avoid guessing a *wrong* project, and a neutral default bucket is not a guess.

From now on "no match" no longer means "dropped"; it means "landed on a placeholder/default, awaiting organize." The historically dropped batch re-enters as placeholder projects when the user runs "Settings → Import now" (`upsertDoc`'s source+title idempotency key makes a re-import an update, not a duplicate).

**4. Automatic "promotion" of placeholder projects, and its built-in exception.** A placeholder's `root_path` is the real repo path, and `root_path` carries UNIQUE — so if that repo is later discovered by a scan, `SyncProjectTx` (`projects.go:121`) hits the same row. Add one rule to `SyncProjectTx`: when it hits an existing `kind='import_placeholder'` row, promote its `kind` to `scanned` (the placeholder becomes a real project seamlessly, notes staying put). **Exception**: claude's identifier is a mangled directory name (`-Users-…-Proj`, `internal/importers/claude/claude.go:115`) that may not equal the real repo path, so it cannot auto-promote and can only be merged by organize — this is documented so nobody treats it as a defect to fix.

**5. Add "knowledge-base organize," at primarily project granularity.** One surface lists note groups sitting under projects with `kind IN ('import_placeholder','default')`. **Primary action**: with one click reassign **all notes** of a placeholder/default project into a user-chosen target real project (reusing the `UPDATE project_notes SET project_id=? WHERE project_id=?` statement from `MergeProjectUp` and the `MoveNote` contract); individual notes can fall back to note-level moves. An emptied placeholder may then be deleted. The organize interaction reuses the batch-approve skeleton from `Review.tsx` rather than building a new queue.

**6. Deletion/cleanup semantics: the default project is protected, and cascading delete is a manual-only option.** Add a "`kind='default'` is never deleted" exemption to `CleanupStaleDataTx` (closing the loophole where Decision 2's seed gets deleted after it is emptied). Placeholders: keep the existing rule (deleted once empty), but when one has notes and no matching repo row — i.e. its source repo has vanished from scanning — mark it in the organize surface as "source repo gone," and let the user **manually** choose "delete it together with its notes." **No automatic cascade deletion** (it clashes with the user's standing "confirm before deleting" preference and violates file/data protection: a destructive action must be a user-decided optional).

**7. Migration shape: standalone v24.** Unlike ADR-0021's preference to batch, this ADR has an **immediate schema consumer** — the `project_kind` column and the default-project seed *are* the foundation of this very feature and cannot wait for some future CHECK rebuild. So open v24, purely additive (1 column + 1 seed row + cleanup/predicate adjustments).

## Options considered (how to express the "headless landing spot")

| Option | Distance from status quo | Value | Main risk |
|---|---|---|---|
| Truly nullable `project_id` (a note may belong to no project) | Far | Conceptually the most "headless" | Breaking `NOT NULL` + FK ripples through FTS / the embedding queue / `ListNotes` joins / cascade / every `project_id>0` assumption; large change surface with no matching product payoff |
| `project_id=0` global sentinel (aligning with `wiki_pages`) | Medium | Consistent with the page layer | AUTOINCREMENT starts at 1 and the FK has no `id=0` target → either insert a fake row or drop the foreign key; and the front-end "All projects" already occupies `value=0`, already at odds with `bindings.go:528`'s "GLOBAL tier ≠ every project" — stuffing note `0` into the same space blurs both |
| **This decision: placeholder + default projects (`project_id` always a valid non-null value)** | Near (reuses `SyncProjectTx` / `SplitProjectDown` / `MoveNote` / `MergeProjectUp`) | No broken schema constraints, notes always owned, floating knowledge gets an explicit landing spot and an organize exit, "where a project came from" becomes visible in data | A batch of placeholder rows "grows" in and needs kind-differentiation and organize cleanup; claude-style sources don't auto-promote |
| Keep status quo (silent drop) | 0 | Cheap | Keeps dropping user knowledge (41 drops already demonstrated) — exactly what this need exists to end |

## Consequences

**Positive**: no more silent import loss (no match → placeholder/default landing); clicking a note changes from "jumped to an empty project" to "reaches the note and highlights it"; floating knowledge finally has an explicit landing spot and a reassignment exit; `project_kind` makes "scanned vs import-placeholder vs system-default" decidable at the data layer, reserving the expression slot for a later "edit a project's associated repo" (not built this round — see pending calls).

**Negative (no varnish)**:
- `projects` gains a column + one seeded default row: touches `ExpectedSchemaVersion` and a reversible-migration test; v24 touching the real database must follow the "rehearse on a copy first" discipline (ADR-0021's amendment record stresses it still governs **every** subsequent migration), with the rehearsal run by the user personally.
- A batch of placeholder projects appears out of nowhere; if organize lags, the dashboard gets "noisy" — kind-differentiation + the organize surface contain it, but visual noise is a new cost.
- A placeholder and a scanned real project may coexist as "same name, different path" (claude's mangled name, or a moved repo), requiring manual merge in organize rather than full automation.
- "Source repo gone → delete its notes" is a manual option: leftovers are cleaned by the user proactively, not automatically — a deliberate trade of tidiness for safety, consistent with this repo's stance on destructive actions.

## Promotion conditions (Proposed → Accepted)

1. **Migration tests**: `project_kind` ADD COLUMN succeeds; the default row is idempotently seeded (running twice still yields exactly one row); reversibility (rebuild/rollback path); `ExpectedSchemaVersion=24` matches the migration count.
2. **Import landing tests**: an `ImportDoc` that matches no project but carries a `RepoPath` → assert a `kind='import_placeholder'` project is created, the note's `project_id` points to it, and `Skipped` no longer grows; a doc without `RepoPath` → assert it lands on the `kind='default'` project.
3. **Cleanup/promotion tests**: an empty default project is **not** deleted by `CleanupStaleDataTx` (the exemption holds); a placeholder with notes is not auto-deleted; after a scan hits the same `root_path` the placeholder's kind is promoted to `scanned` (`SyncProjectTx`).
4. **Organize tests**: after a project-level reassignment the target project's note count grows and the source placeholder empties; the "source repo gone → manual delete" path correctly deletes the notes along with it, and the default project **never** enters that deletion path.
5. **One live-DB copy rehearsal** (read-only source + disposable copy, following ADR-0021's "rehearse on a copy first" discipline): reconcile the migration and seed on the copy, then the user personally advances v24 onto the real database.
6. **Bilingual docs in the same batch**: `docs/**` and `docs/en/**` changed together (import landing, knowledge-base organize, click-a-note-direct, meaning of placeholder/default projects), and `CHANGELOG.md` records an `[Unreleased]` entry; `docs/**/*.html` are build artifacts and are never hand-edited.

## Implementation corrections (facts obtained when this landed, 2026-10-16)

Places where reality disagreed with the design, recorded so the next person does not rediscover them:

1. **The landing helper is `EnsureImportPlaceholder(db *sql.DB, repoPath, repoName)`, not the `EnsureImportPlaceholderTx` Decision 3 named.** The runtime's `upsertDoc` runs on a non-transactional `*sql.DB` (`GetNoteBySourceTitle` / `CreateNoteEx` take `r.db`), so the landing decision sits naturally in the `TriggerImport` loop and the helper takes a `*sql.DB`, not a `*sql.Tx`. A `GetDefaultProjectID(db)` helper (not named in the decision) was added for the repo-pathless landing and the organize view. `repoName` is the reserved slot for sources like claude that carry a decoded label but no real path (the placeholder is named with it, its `root_path` is a synthetic URI `import://claude/<mangled>`, so a claude placeholder never auto-promotes — consistent with Decision 4's exception).

2. **A consumer-layer split by `project_kind` emerged at implementation time that the decision did not spell out.** An always-present default row has side effects: without the split, (a) `ResolveProject`'s "single project auto-resolve" would never pin (one more candidate every time) and the disambiguation catalog gets polluted; (b) an agent picking a placeholder/default id from `repotory_projects_list` then calling `repotory_context` would get nothing; (c) integrity's `scan_coverage` would read the non-scan default/placeholder rows as "discovered but never collected" and warn permanently. So the implementation: the AI context resolver and `ListProjects` (the MCP surface) consider only `scanned`; `scan_coverage`'s three counts gained a `project_kind='scanned'` predicate; the desktop dashboard's `GetProjects` still shows default/placeholder (badged). `ListProjects` was verified repo-wide to serve only the MCP surface, so filtering it does not touch the UI.

3. **The always-seeded row broke a batch of tests that assumed it away.** default takes `id=1`, so "the projects table is only user projects" and "fresh install = 0 projects" stop holding: `projects_level_test.go` (split/merge counts + a "any project that isn't the pid" loop that would mistake default for the split child), `service/project_level_test.go` (scanning an id range for live projects), `service_test.go` (GetProjects count), the `cmd/mcp` list/context tests, `context_test.go` (`ResolveProject("1")` and a hardcoded `| 1 | alpha |` catalog assertion), and `toolcopy_test.go` (pins "current version = v23") all needed changes. **The fix was to filter by kind or locate by the returned pid — not to hide the default** (the UI must show it for the landing to be real).

4. **The migration entry is `{id: 24, fn: EnsureProjectKind}`, and `EnsureProjectKind` doubles as an unconditional InitDB self-heal** (the v22/v23 pattern): the ALTER's "duplicate column name" is swallowed by `isAlreadyExistsErr`, and the seed's `WHERE NOT EXISTS` is idempotent. The column is added via `ADD COLUMN ... NOT NULL DEFAULT 'scanned'` (a constant default satisfies SQLite), with no inline CHECK.

5. **codebuddy-memory was folded into the unified landing at the user's call**: it previously did `return docs, nil` when no target was configured; it now lands on "Uncategorized", superseding that importer's own earlier intentional behaviour (Decision 3 originally named only openclaw/hermes).

6. **Organize landed as 3 desktop-only RPCs** (`ListOrganizeGroups` / `ReassignLandingNotes` / `DeleteLandingProject`), registered in `internal/app/surface.go`'s `bindingSurfaces` (`SurfaceDesktopOnly` + Reason, no MCP twin; pinned by `TestBindingSurfaceRegistryIsComplete`). `ReassignLandingNotes` is a **single transaction that moves notes only** (not todos); the target may be `scanned | default` but never another placeholder or itself; `DeleteLandingProject` accepts only `import_placeholder` (default/scanned always refused), and a non-empty one needs `deleteNotes=true` as explicit confirmation. On the front end `OrganizeGroup.project_kind` / `Project.project_kind` are typed **optional** (Go always sends them; optional keeps old mocks compiling); the click-a-note highlight defers its `setState` through `requestAnimationFrame` to satisfy `react-hooks/set-state-in-effect`.
